# ChunkCard Governance Positioning

## Core Position

ChunkCard should be treated as governed semantic infrastructure rather than ad hoc content formatting.

## Structural Signals Already Present

- Stable identifiers (`chunk_id`).
- Source lineage (`source`).
- Verbatim preservation (`raw_text`).
- Normalized abstraction (`normalized_template`).
- Audience surfaces (`surface`).
- Dependency graphing (`dependencies`).
- Monetization mappings (`revenue_levers`).
- Risk controls (`risk_controls`).
- Lifecycle state (`status`).

## Architectural Interpretation

The current model already overlaps with:

- Semantic chunking.
- Provenance-aware retrieval.
- Governance tagging.
- Deployment templating.
- Modular knowledge packaging.

## Publication Boundary (Recommended Split)

Publish publicly:

- Doctrine and glossary.
- Canonical ontology and routes.
- Rights boundaries and machine-readable metadata.

Keep private until IP perimeter is hardened:

- Ingestion and normalization logic.
- Prompt orchestration and scoring logic.
- Retrieval transformation layers.
- Internal training structures.

## Interface Mapping

- `ChunkCard`: private ingestion unit.
- `/canonical`: public ontology index.
- `/llms.txt`: crawler-facing machine map.
- `/ai-rights.txt`: machine-use boundary.
- JSON-LD: structured identity graph.

## Operating Principle

Preserve essence and swap surfaces: maintain operational invariants while allowing audience-specific packaging.
