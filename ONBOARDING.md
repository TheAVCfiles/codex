# ONBOARDING

## Welcome

This repository is evolving from experimental development storage into governed memory infrastructure.

The objective is not simply to store code or notes.

The objective is to preserve provenance, structure transformation pipelines, govern asset promotion, and separate raw signal from enterprise-grade delivery.

## Core Principle

> Clean front door, preserved roots.

Every promoted asset should maintain traceable lineage back to its source archive.

## Repository Classification Model

### 1. Archive Repositories

Purpose:

- preserve raw experiments
- retain lineage
- freeze source states
- store abandoned or exploratory work

Characteristics:

- messy allowed
- provenance-first
- minimal polish
- restricted publication

### 2. Enterprise Repositories

Purpose:

- client-safe systems
- investor-readable infrastructure
- governed commercial assets

Characteristics:

- documented
- reviewed
- structured
- operationally stable

### 3. Room Interface Repositories

Purpose:

- user-facing digital rooms
- onboarding experiences
- retrieval/export/intake systems
- governed interaction layers

Characteristics:

- UX-first
- access-controlled
- presentation-safe
- workflow-driven

## Before Contributing

Before promoting or publishing any asset:

1. Record provenance.
2. Record source SHA/tag.
3. Classify the asset.
4. Assign an asset score.
5. Complete safety/visibility review.
6. Determine licensing and payment posture.

## Required Enterprise Files

Promoted repositories should include:

- `README.md`
- `PROVENANCE.md`
- `STATUS.md`
- `LICENSE.md`
- `CHANGELOG.md`
- `ONBOARDING.md` or `USAGE.md`
- `PAYMENT.md` or `NONCOMMERCIAL.md`

## Operator Guidance

Avoid:

- copy-paste lineage destruction
- publishing raw experimental debris as production systems
- mixing client-safe infrastructure with archive dumps
- removing provenance records during refactors

Prefer:

- governed promotion
- layered architecture
- explicit operational posture
- clean interfaces with preserved roots
